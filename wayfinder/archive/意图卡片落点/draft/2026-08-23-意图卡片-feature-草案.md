# 意图卡片 Feature 草案 · 落地后的整体图景

> 本草案是 Wayfinder 之后的又一轮产出。九张票定了每个局部怎么落，实现计划（`plan/2026-08-22-intent-cards.md`）定了任务怎么拆，这份文档补的是两者都没有的东西：把整条链路当作一个整体讲一遍——用户会经历什么、数据经过几段管线、一张卡从生到死经过谁的手、生成这件事归哪个 Agent、Tools 开多大、以及落地之后怎么知道它做得好不好。
>
> 产品目标先立在这里，后面所有章节都对它负责：**意图卡片要制造 aha moment**——挖出用户自己没意识到的模式，或者主动给出下一步工作的执行 action，替用户省掉一段脑力劳动。2026-08-23 用户据此推翻了「v1 单次直调」的原 T3 决议，生成段改为 Pi 子进程会话（修订见 T3/T7 票内记录），本草案已按修订后口径书写。

## 一、用户看到的交互逻辑

先按时间顺序走一遍一个普通用户的日子。

**后台（无感）。** 只要 Cue 的采集引擎在跑（托盘挂着即可，主窗口可以不开），Rust 侧有一个随引擎常驻的心跳循环（T3 决议 3）。每 15 分钟醒来一次，先看这 15 分钟里用户有没有值得注意的活动：窗口切换和焦点事件攒够 3 次，或者画面内容变化够 5 次（D3 常量）。没过门槛就回去睡觉，什么都不发生。

**出卡那一刻。** 过了门槛，心跳取一份 activity-summary 有界摘要连同窗口信号，起一个 Pi 子进程会话（默认供给内置 Ollama，设置页有 BYOK 引导可换云端强模型，T7 修订）。会话里挂着只读工具白名单和基线 skills，模型可以自行去本地数据里查证补充，最后交出方案 JSON。落库之后两件事同时发生：主窗口工作台的数据列表收到刷新事件；右上角的通知面板弹一条提醒。提醒走 notification-panel 现成的闸门——静音、勿扰、冷却都照旧生效（T5 决议 2），被抑制也算通过验证。

**裁决。** 点开提醒进主窗口的「工作台」section（左栏新增一行，照 activity/pipes 的现成模式，不动 chat 首屏，T5 决议 1）。列表两个 Filter：待决定、已结束。一张提案卡长这样：一句 proactive_view 说明为什么给你这张卡，下面是方案列表——推荐项预选，选中后显示后果行，末行是「自己写一个新方案」的输入框（T6 定稿）。按钮两个：「接受选中方案」「不要」。轻提示卡没有方案列表，只有正文加「知道了 / 不要」。

**接受之后呢？第一版：什么也不发生。** 接受只写终态，不开 Thread，不触发执行（T5 连带收窄）。唯一的例外是新手接入卡：点「接入」会在写终态之外调 `skills.rs` 现成的连接机制，把 Cue 的本地 API 注册进检测到的第三方 agent 的 MCP 配置里（D5，全计划唯一 accept 带副作用的路径）。

**设置页。** 模型区多一块 intent 槽卡片：preset 选择器（含「跟随 Chat（默认）」选项）、当前实际生效的来源与端点 host、最近一次生成的成败与失败原因，外加一块 BYOK 引导——说明这个功能吃模型能力，推荐给槽位配云端强模型（T7 + R7 + T7 修订）。生成失败不打扰工作台，心跳下轮自然重试。

## 二、链路里有几条 Pipeline

按「数据从哪来、经过哪些加工、到哪里去」数，v1 全链路一共三段，其中本 feature 新建一段半：

| # | Pipeline | 宿主 | 状态 |
| --- | --- | --- | --- |
| P0 | 采集管线：frames / elements / ui_events 持续落库 | screenpipe-engine | fork 已有，本 feature 只消费 |
| P1 | **生成管线**（新建）：心跳 tick 内的顺序流程，含一次 Pi 会话 | src-tauri `intent_agent::runner` | 本 feature 新建 |
| P2 | **裁决管线**（新建）：事件监听 → 列表渲染 → shown 回写 → decide 写终态 | 前端 workbench + Tauri commands | 本 feature 新建 |

P1 展开是固定顺序的步骤（Plan Task 4 的 tick 编排，出口已按 T3 修订更换）：结算过期 → 读最近一张卡时刻算查询窗口 → 数增量信号 → 过门槛 → GET activity-summary → 解析供给（intent 槽 preset → chat 镜像现查 → 内置 Ollama 三级回退，D1/T7）→ 起 Pi 会话（只读白名单 + 基线三件 skills，超时即失败）→ 解析会话终报 JSON → dedup 入库 → emit 事件 + 发通知。任何一步失败记 tracing 进设置页状态，循环不退出。

P2 是唯一能改卡片状态的通道：前端按钮只调 command，SQL 层带 WHERE status 守卫，模型侧没有任何路径能写 status（T8 决议 4 + R1）。Pi 会话再多轮，产出的也只是终报文本；写库这件事永远在 Rust 侧确定性代码手里。

两条不算独立管线的旁路：

- **过期结算**挂在 P1 的节拍上，每次心跳醒来先做，不建独立定时器（T8 决议 3）。
- **新手接入卡**走一个专门的 Tauri command 直接进 P1 的后半段（构造固定 plans → 入库 → 推送），跳过心跳、门槛和模型会话（T3 决议 6、D5）。它是开发期测通整条链路的载具。

## 三、一张意图卡片的生命周期

```
                    insert (runner 或 onboarding command)
                              │
                              ▼
                         ┌─────────┐
          前端渲染回写    │ proposed │  「正在准备」：库里存在，界面短暂过渡
      ┌─────────────────►└────┬────┘
      │   mark_shown          │
      │   （单向，不可重复）   │
      │                       ▼
      │                  ┌─────────┐
      │                  │  shown   │ expires_at = shown_at + 48h
      │                  └──┬─┬─┬──┘
      │        decide("accepted")││decide("rejected")
      │              ▼           │▼
      │        ┌──────────┐      │   ┌──────────┐
      │        │ accepted │      └──►│ rejected │
      │        └──────────┘          └──────────┘
      │                                      
      │            心跳结算 expire_due：expires_at 到点且仍 shown
      │                    └──────────────► ┌─────────┐
      │                                     │ expired │
      │                                     └─────────┘
```

几个口径（全部出自 T4/T8，这里集中复述）：

- **proposed 与 shown 分开**，是为了让 48 小时的过期时钟从「用户有机会看到」起算——主动式生成可能发生在没人看着屏幕的时候。
- **时钟不可续命**。mark_shown 单向守卫，重挂载、双渲染、多窗口的重复调用都被 SQL 拒绝，shown_at 不改写（R1）。
- **三个终态分开存**（accepted / rejected / expired），为将来的反馈账留信号；v1 的 evaluation 就靠这个设计白拿数据，见第七节。
- **去重**：unique(dedup_key, local_date)，dedup_key = `{card_type}:{dominant_app}`（D2）。产品含义是「每个 app、每种类型、每天最多一张」。
- **新手卡不过期**（expires_at = NULL，T4 决议里的可空单列），不计徽标。
- 对 Cue 合同《04》的两处有意偏离已有票面理由：轻提示免过期的规则被统一 48h 取代（T8 决议 2）；重写流程整个砍掉（T4 决议 1）。

## 四、生成由哪个 Agent 负责：一个跑在定时节拍上的 Pi 会话

**v1 的 Intent Agent 是真实存在的运行时实体了**：一个 Pi 子进程会话，与 chat 同一套 runtime、同一套启动模式（`piStart / piPrompt / piStop`，先例 `lib/daily-summary-pi.ts`）。区别在宿主方式——chat 由用户消息驱动，意图会话由 Rust 心跳在门槛过后拉起，跑完一轮拿到终报就退出。

为什么从单次直调改成会话（T3 修订的两个理由）：

1. **aha moment 需要挖掘深度。** activity-summary 是主进程预先聚合的固定视角，直调模型只能在这个视角里做阅读理解；而「用户没想到的东西」往往藏在摘要压缩掉的部分里。会话形态下模型能拿着只读工具自己去查证，「材料不足」也从一句客套话变成查过之后的有据结论。
2. **基础设施一次付清。** 后面发现效果不好要加工具，改的是白名单配置，不再是架构。升级循环从「一次工程改动一轮」变成「一行配置一轮」。

不变的东西同样重要：心跳、门槛、查询窗口、dedup、落库、状态机、展示全部沿用原决议；输出契约不变——会话终报必须是带 `"v":1` 的方案 JSON 或 `{"insufficient_material":true}`，parse 层原样复用；会话超时或格式不符记失败，心跳下轮重试，不搞双路径回退。新手接入卡仍是确定性旁路，不起会话不走模型（D5）。

## 五、Tools 与 Skills：只读白名单加基线三件

Pi 会话默认继承 chat 的全量工具面，所以「不给它加 tools」不是一个可选项——不显式收窄就是全开。经用户裁决，v1 第一天的配置是：

| | chat | 意图卡片 v1 |
| --- | --- | --- |
| 运行时 | Pi 子进程会话 | Pi 子进程会话（同款） |
| 工具面 | 全量：extensions 注册的 sp_* 系列、skills、内置 bash/read，未设 allowedTools 即全开 | **只读白名单**：sp_mcp_list_tools / sp_mcp_call 等 Cue 数据读取类；禁 bash、禁一切写侧工具 |
| skills | 基线集 + 用户自装全量镜像 | **仅基线集**（core 现状：screenpipe-api / screenpipe-cli / render-html-report） |

两条禁令的理由都来自同一个事实：这是无人值守的定时任务。bash 和写侧工具意味着周期性任意执行能力；用户自装的 skills 是周期性执行一段任意导入指令。chat 里有人盯着，风险性质不同。精确白名单清单实现期对照 `pi.rs` 的 `apply_pi_tool_allowlist` 机制定，候选以 sp_mcp 桥接 Cue 自家 MCP server 的读取路由为主。

基线集 skills 则是明确要的：它们教模型怎么查本地数据，正好服务挖掘目标，且写入机制现成（`ensure_screenpipe_skill` 写入后需剔除用户镜像目录，实现口径见 Plan D7）。用户自装 skills 将来可以做成开关再议，v1 不进。

## 六、落库

一张卡在库里就是 `intent_cards` 表的一行，十二列（T4 定稿，DDL 见 Plan Task 1）：身份（id、origin、card_type、dedup_key、local_date）、内容（proactive_view、plans_json）、供给追溯（model_id）、生命周期时间戳（created_at、shown_at、expires_at）、状态（status）。

写入路径的唯一性是这张表的纪律，三条各对应一个来源：

| 写什么 | 谁能写 | 入口 |
| --- | --- | --- |
| 新卡插入 | 心跳 runner、新手卡 command | `insert_intent_card`（dedup 命中返回原 id） |
| 状态转移 | 前端经 Tauri command | `mark_shown` / `finish` / `expire_due`，SQL WHERE 守卫 |
| plans_json | 仅 runner 序列化会话终报 | 结构带 `"v":1`，未知版本拒解析（D4） |

明确不在库里的东西同样重要：rejected 没有理由字段，没有 feedback 表，没有 input_scope 记账三件套（T4 明确不带清单）。这些缺口直接决定了下一节的 evaluation 天花板。

## 七、后续 Evaluation 怎么追【新增提案】

Wayfinder 把反馈账划出了范围，但「落地后怎么知道这功能值不值」总得有个答案。以下分层提案不动 v1 schema，只声明哪些信号免费可得、哪些要等补票。衡量标尺是第一节立的产品目标：aha moment 有没有发生。

### L0：v1 上线当天就能算的（零迁移）

库和日志里已经埋好的信号，定期跑查询脚本即可：

- **采纳率**：accepted 占三个终态的比例，按 card_type、model_id、endpoint 来源分桶。五值状态分开存就是为此留的（T4 决议 4）。这是离 aha moment 最近的代理指标——没人接受的卡谈不上惊喜。
- **响应时延**：created_at → shown_at → 终态的时间差分布，看卡片是不是在被及时看到和处置。
- **过期率**：expired 占比过高说明出卡时机不对或 48h 太短，这是对 T8 统一口径的实证检验。
- **材料不足率**：insufficient_material 出现的频率。会话形态下这个指标多了含义——模型是查证过后才说材料不足的，连续过高说明门槛或指令该调了。
- **生成健康度**：会话失败率、超时与格式错误分布、三级回退的实际命中比例。
- **会话轨迹留存**：Pi 会话天然留下 transcript，排查某张烂卡时能看到模型的完整推理与工具调用过程——比直调时代的一条日志可诊断性强一档，这也是会话形态白送的红利。

建议把这组指标的定义（SQL 口径）写进实现期的验收清单，作为端到端测通之后的收尾步骤。

### L1：跑一段时间后的补票候选

L0 回答「卡片有没有被人要」，回答不了「为什么不要」。rejected 无理由、无轻重量级反馈通道，是 T4 有意砍掉的。等真实数据积累出问题再回来补，候选形态二选一：`rejected_reason` 加列（rebuild 迁移，代价已知，Schema 备忘有先例），或独立的 `intent_card_feedback` 小表。不做预先设计。

### L2：执行链路落地后才可能的事

意图卡片的真实价值是「接受的方案被执行并解决了问题」。v1 接受只写终态、无执行链路，价值闭环天然测不到——这是 v1 evaluation 的天花板，不是缺陷。执行链路 effort 启动时（MAP Out of scope 第一条），evaluation 应作为该 effort 的一等公民一起设计，而不是事后追加。

## 八、与既有产出的关系

- 第四节第五节的机制事实核对过 fork 当前代码（pi.rs 的 allowlist 与 skills 镜像、skills.rs、daily-summary-pi.ts、activity_summary.rs）。
- 第七节是新提案，若采纳，L0 部分并入 Plan 的验收清单，L1/L2 留给将来的开票裁量。
