# T8 · 审批交互与状态机实现

## Question

五值状态机（`proposed → shown → accepted/rejected/expired`）与按钮-状态收口表照搬合同，剩余是实现裁决：48 小时过期的定时器放宿主哪一层（Rust 侧调度还是前端惰性结算）？铅笔编辑只写 `adjust_opened_at` 的交互边界怎么划？「有人动才重置过期」的判定口径？快捷键 gap 是否在本轮定义（04 篇未规定）？

## Resolution

Status: Resolved
Claimed by: pis（2026-08-22，与用户逐项裁决）

### 决议

1. **状态机五值照搬《04》§1，v1 生效的转移收窄为四条**：`proposed → shown`（前端实际渲染后经 command 回写 `shown_at`）、`shown → accepted`（接受或「知道了」）、`shown → rejected`（不要）、`shown → expired`（定时结算）。铅笔自环随 `adjust_opened_at` 不建列（T4 已定）而消失。
2. **过期口径维持 T4：全类型统一 48h**。这是对《04》§3「轻提示不过期、一直可接受」的有意偏离，理由：v1 让三类卡共用一套生命周期，到期统一离开待决定，避免轻提示在队列里无限堆积。将来若轻提示被过早清走成为实际问题，回合同口径即可——`expires_at` 单列可空，不需要迁移。
3. **过期结算挂 T3 心跳节拍**：Rust 每次醒来先结算 `expires_at <= now` 且仍处 `shown` 的卡，再做出卡判据；不建独立定时器。主窗口开不开都不影响结算，排除前端惰性结算的漏结风险。
4. **状态写入唯一入口是 src-tauri 的 Tauri command**——即《04》§2「主进程确定性准入」在 fork 的对应物：前端按钮只调 command，不直接写库；模型侧没有任何路径能写 `status`。
5. **「有人动才重置过期」在本图消解**：重写砍掉、adjust 不建列之后，不存在非终态的用户动作；接受与不要直接进终态，无需重置判定。《04》§3 那段判定口径整体随执行链路 effort 回补。
6. **快捷键不在本轮定义**：《04》未规定，fork 没有卡片快捷键先例；T6 原型若显示需要，再补票。

### 对 T4 的补记

第 6 条决议的统一 48h 口径与本票第 2 条的关系已在 T8 落档，T4 正文不改。
