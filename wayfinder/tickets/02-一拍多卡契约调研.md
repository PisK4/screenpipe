## Question

当前契约是一拍一卡（`instruct.rs` 的任务行写死「产出一张新的意图卡片」，`parse::parse_model_output` 与 intent-card.ts 同步该契约）。调研在 Pi 子进程会话架构下支持**一拍多卡**的实现路径：

1. `submit_intent_card` 在同一会话内被多次调用时，现有 parse/落库链路会发生什么（截断？覆盖？报错）？
2. 多卡的两种契约形态各自的影响面：(a) 允许工具多次调用；(b) 单次载荷改为卡片数组；
3. 前端工作台列表、DB intent_cards 表、软去重（对照近 48h 清单自行判重）各自要不要跟着动；
4. 给出成本清单与推荐形态，供 T3 裁决。

相关文件起点：`apps/screenpipe-app-tauri/src-tauri/src/intent_agent/`（mod.rs / instruct.rs / parse / session.rs）、`crates/screenpipe-engine/src/routes/intent_cards.rs`、`doc/FEATURE_INTENT_CARDS.md`、上张图归档票 `archive/意图卡片落点/tickets/04-数据契约落库.md` 与 `10-软去重重设计.md`。

## Resolution

Status: Resolved（2026-08-25，只读代码调研，未运行验证）

### 1. 现状：同一会话内多次调用 submit_intent_card 会发生什么

关键事实是**落库不发生在工具内**：`intent-card.ts` 的 `execute()` 只做参数校验并返回一句确认文本，卡片真正插入发生在会话结束后的宿主侧（runner.rs）。因此多次调用的行为完全由「最终报告收集」决定：

- `session.rs::structured_card_from_agent_end` 遍历 `agent_end` 的 messages，把**最后一个**名为 `submit_intent_card` 的 toolCall 块的 arguments 作为最终载荷（有测试 `structured_card_extraction_takes_the_last_call_and_ignores_other_tools` 钉死此语义）。
- 所以同一会话内多次调用既不截断也不报错——**前面的调用被静默覆盖，只有最后一次落库**。模型侧每次都收到 "Intent card submitted." 的成功回执，与实际只有一张卡生效的事实不一致。
- `{"insufficient_material": true}` 同样经该工具的 arguments 传递（parse.rs 对载荷先查此键），覆盖语义对它同样成立：先交卡再改口材料不足（或反过来），以最后一次为准。
- 文本路径兜底（text_delta 缓冲 / agent_end messages 拼接）只在结构化提取为空时启用；parse 拒绝非 JSON 文本。

### 2. 两种多卡形态的影响面

**(a) 允许同一会话内多次调用**

- 收集侧：`structured_card_from_agent_end` 改为收集全部匹配块返回 Vec；`run_intent_session` 返回类型随之变为 Vec<String>。
- 落库侧：runner.rs 的 `ModelOutcome::Card` 分支从单次 insert+emit+notify 改为循环。每张卡独立走现有 `insert_intent_card`。
- 契约文本：instruct.rs 任务行「产出一张新的意图卡片」改为允许多张；intent-card.ts description 相应放宽（工具本身逻辑不用动——它本来就无状态、可重复调用且逐次校验纠错）。
- 不用动的：parse.rs 逐载荷解析不变；DB 表与 insert 不变（软去重落地后 dedup_key 仅记录字段、无唯一索引，同拍多卡不撞约束）；前端工作台按列表查询 + 逐卡 `intent_card_created` 事件刷新，天然支持多卡；引擎路由 intent_cards.rs 是纯读侧，无关；SKILL.md 判重学说按卡粒度表述，无需改。

**(b) 单次载荷改为卡片数组**

- 契约升级：intent-card.ts schema 加 `cards: [...]`（或升 v=2），parse.rs 的 GeneratedCard/版本门同步改，两侧加测试。
- 校验语义变差：数组里一张卡非法会导致整个载荷被拒或需要部分接受逻辑；而形态 (a) 下每次调用独立校验、独立 corrective error，天然部分成功。
- 载荷体量风险：runner.rs 注释记录过教训——材料里带全量 proactive_view 曾把响应预算压死（trace 01a033b6/01a03407），单载荷塞多张卡放大同类风险。
- 下游影响面与 (a) 相同（insert 循环化），但额外背上双端 schema 版本迁移成本。

### 3. 成本清单

| 形态 | 必改文件 | 不改 |
| --- | --- | --- |
| (a) 多次调用 | runner.rs（循环 insert/notify）、session.rs（收集全部调用）、instruct.rs（任务行措辞）、intent-card.ts（description 措辞）、相关测试 | parse.rs、DB、engine 路由、前端、SKILL.md |
| (b) 数组载荷 | 上述全部，另加 parse.rs 与 intent-card.ts 双端 schema/版本门迁移、部分失败语义设计 | DB、engine 路由、前端 |

未验证项（如实声明）：pi 运行时是否允许模型在同一轮内连续多次成功调用同一工具后继续推进到 agent_end，本次为静态阅读未跑会话验证；(a) 形态下若模型习惯性只调一次，行为退化为现状一拍一卡，属安全退化。

### 4. 推荐

**推荐形态 (a)：允许同一会话内多次调用。** 理由：(1) 影响面最小，四个文件以内且全部在生成链路内部，DB/前端/引擎零改动；(2) 工具层已有逐次校验与纠错回执，多次调用天然获得部分成功语义，避免数组形态的单点失败与双端版本迁移；(3) 避开单载荷膨胀压垮响应预算的已知风险。需配套一条护栏：单拍出卡数设上限（建议复用 plans maxItems=3 的量级），防止失控刷卡。
